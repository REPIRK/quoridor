# Quoridor

Настольная игра Quoridor для Windows: доска 9×9, по 10 стен на игрока, полный набор
правил (прыжок через фишку, диагональный обход у стены, запрет полной блокировки пути).

Режимы: **Local match** — двое за одним ПК, **Play the bot** — против ИИ с тремя
уровнями сложности, **Watch two engines** — движок против движка, можно просто
смотреть. Дополнительно настраиваются часы (выкл / 5+3 / 3+2) и то, ходите вы первым
или вторым. Интерфейс на английском, тёмная и светлая тема с плавным переходом цвета.

Если выбрать «ходить вторым», доска разворачивается: ваша фишка всегда у ближнего
края, независимо от того, какой цвет вам достался.

## Запуск

```bash
dotnet run --project src/Quoridor.App/Quoridor.App.csproj -c Release
```

Собрать один самодостаточный `.exe` (не требует установленного .NET на целевой машине):

```powershell
powershell -ExecutionPolicy Bypass -File publish.ps1
```

Результат: `publish/Quoridor.exe`.

Прогнать проверки правил и движка:

```bash
dotnet run --project tests/Quoridor.Selftest/Quoridor.Selftest.csproj -c Release
```

## Управление

| Действие | Как |
| --- | --- |
| Ход фишкой | клик по подсвеченной клетке |
| Поставить стену | навести на паз между клетками, клик |
| Повернуть стену | правая кнопка, колесо или `R` |
| Показать маршруты | `Space` или кнопка **Routes** |
| Листать историю | `←` `→`, кнопки **◀ ▶ Live** или клик по строке журнала |
| Отменить ход | `Ctrl+Z` |
| Начать заново | `F2` |
| Меню | `Esc` |
| Тема | `Ctrl+T` |
| Полный экран | `F11` |

Режим стены не переключается вручную: положение курсора само решает, целитесь вы в
клетку или в паз между клетками. На пересечении пазов ориентация берётся из
последнего выбора, `R` её меняет.

## Структура

```
src/Quoridor.Core     правила и представление позиции, без UI
src/Quoridor.Engine   агенты: оценка, эвристический бот, alpha-beta поиск
src/Quoridor.App      WPF-приложение
src/Quoridor.Web      браузерная версия (Blazor WebAssembly)
tests/Quoridor.Selftest  проверки правил и движка без внешних зависимостей
tests/Quoridor.Bench     замеры движка
```

Зависимость строго в одну сторону: `App`/`Web` → `Engine` → `Core`. Ядро никогда не
знало про UI — именно поэтому браузерная версия переиспользует и его, и движок **без
единой правки**: заново написано только представление.

## Браузерная версия

`dotnet run --project src/Quoridor.Web -c Release` — и игра открывается на localhost.
Тот же движок, скомпилированный в WebAssembly.

Одна важная оговорка: интерпретируемый WebAssembly считает **в десятки раз медленнее**
десктопа. Поэтому публикация идёт с AOT-компиляцией (`RunAOTCompilation`), которая
требует workload `wasm-tools` — CI его ставит сам. Замер из дебюта при бюджете 0.6 с:

```
интерпретация   глубина 5     3 818 узлов
AOT             глубина 8    76 401 узел
```

Плата — сборка занимает минуты вместо секунд и 3 МБ в brotli на загрузку. Три полухода
глубины того стоят.

В браузере один поток, и поиск идёт на нём же. Поэтому перед вызовом движка страница
отдаёт кадр браузеру — иначе надпись «Thinking» появилась бы уже после того, как думать
закончили.

### Игра вдвоём по сети

Сайт лежит на статическом хостинге — **сервера там нет и не может быть**, значит и
ретранслировать ходы через свой бэкенд нельзя. Два браузера соединяются напрямую по
WebRTC: создаёте игру, отправляете ссылку, партия начинается в момент, когда её
откроют. По каналу летит нотация хода (`e2`, `e6h`) с номером полухода — дубликат или
сообщение, обогнавшее другое, отбрасывается, а не додумывается.

Бесплатный публичный сервис нужен ровно один раз, чтобы браузеры нашли друг друга.
Дальше в цепочке нет никого, и уже идущая партия переживёт его недоступность. Два
честных ограничения: пока он лежит, **новую** игру не начать, а часть строгих сетей
блокирует прямое соединение. Полноценный сервер-ретранслятор чинит и то и другое — но
его надо где-то держать.

## Ядро: как устроена позиция

`GameState` — изменяемая структура ~96 байт. Поиск копирует её (`var next = state;
next.Apply(move);`) вместо реализации отката хода: это дешевле пары кэш-линий и
убирает целый класс ошибок.

Множество клеток — битборд в `UInt128`: 81 бит, `индекс = строка * 9 + столбец`.
Четыре битборда `Blocked*` отвечают на вопрос «можно ли с этой клетки шагнуть в эту
сторону» одним `AND`. Края доски записаны в них при создании, поэтому ни генерация
ходов, ни поиск пути ни разу не проверяют выход за границы.

Поиск пути — это заливка по битам: один шаг расширяет весь фронт четырьмя сдвигами и
четырьмя `AND`. Замер из `Quoridor.Selftest`:

```
shortest path: 31 ns/call
```

Это важно потому, что проверка «стена не заперла игрока» вызывает поиск пути дважды
на каждую из ~128 стен-кандидатов в каждом узле дерева. При 31 нс полный перебор
легальных стен в узле стоит около 8 мкс.

## Движок

`IQuoridorAgent` — единственное, что видит интерфейс.

* **Easy** — идёт по кратчайшему пути, иногда ставит стену.
* **Normal** — `HeuristicAgent`: перебор кандидатов на один полуход по статической оценке.
* **Hard** — `SearchAgent`: полноценный alpha-beta движок.

### Поиск

`SearchEngine` — negamax с принципиальным вариантом (PVS) и итеративным углублением:

* **Таблица транспозиций** на Zobrist-хеше. Записи — два 64-битных слова, ключ хранится
  как `hash ^ data`, поэтому разорванная запись не проходит проверку на чтении и просто
  считается промахом. Это делает таблицу безопасной для общего доступа из потоков без
  единой блокировки. Корзина — две записи (они всё равно в одной кэш-линии), и места в
  ней неравноправны: первое защищено глубиной, второе перезаписывается всегда. Ранжировать
  оба места по глубине и вытеснять меньшее — очевидная схема, но тогда поток мелких узлов
  вымывает глубокие результаты, ради чего разделение и сделано.
* **Упорядочивание ходов**: ход из таблицы, два killer-хода на полуход, затем стены.
  Ближе к корню они отсортированы по реальному изменению маршрутов; на мелкой глубине,
  где это слишком дорого, — по истории отсечений. На равной глубине история дала 13:11
  за 24 партии, то есть в пределах шума: оставлена как теоретически обоснованная и
  почти бесплатная, но записывать её в победы не за что.
* **LMR** — поздние стены ищутся с уменьшенной глубиной; всё, что превысило alpha,
  переискивается на полной.
* **Аспирационные окна** от глубины 4.
* **Точный эндшпиль**: когда стен не осталось ни у кого, партия — чистая гонка, и
  результат считается формулой, а не поиском. Запас в один шаг покрывает возможный
  прыжок через фишку.
* **Повторения** позиций (включая уже сыгранные в партии) оцениваются слегка в минус,
  чтобы движок не «топтался» вместо игры.

Ветвление режет `MoveCandidates`: рассматриваются только стены, касающиеся клеток на
текущих маршрутах игроков, соседние с уже стоящими стенами и вплотную к чужой фишке.
Это ~30 кандидатов вместо ~130.

Легальность стены обычно стоит двух поисков пути — «не заперли ли кого». `WallGraph`
снимает **82%** этих проверок: стена может разрезать доску, только если минимум две из
трёх её точек (два конца и середина) уже упираются в край или в другую стену. Середину
легко упустить — стена длиной в две клетки, и перпендикулярная стена может примкнуть к
ней посередине. Проверка проверяется перебором в `Quoridor.Selftest`.

### Оценка

Разница длин кратчайших путей — основной вес. К ней два неочевидных слагаемых.

**Запас стен** стоит дорого (180 против 100 за шаг маршрута). Изначально он стоял на 34,
и движок с треском проигрывал: он спускал все десять стен в дебюте за временный отрыв,
а потом соперник с восемью стенами в руке спокойно его замуровывал.

**Вердикт гонки** — кто добежит первым, если оба просто пойдут. Без него оценка слепа:
когда оба идут, каждый шаг сокращает оба маршрута и разница не двигается, так что
выигранная и проигранная гонка выглядят одинаково. Но это обрыв, а не наклон, и
глубокий поиск охотно гоняется за переворотом вердикта, который стены потом отменят —
поэтому вес умеренный и убывает с числом стен, оставшихся в игре.

Оба веса подобраны матчами на равной глубине (`bench duel`): стена 180 обыграла 120 со
счётом 12:4, вердикт 220 обыграл 120 со счётом 18:6. Веса связаны — пока стена стоила
120, лучшим вердиктом был 120, а после её переоценки оптимум уехал вверх.

### Цена узла

Узкое место движка — не хитрость отсечений, а стоимость узла, и она почти вся сидела в
поисках пути при работе со стенами. Две правки:

1. Для упорядочивания больше не считается собственный маршрут у стен, которые сопернику
   ничего не дают: такие сразу уходят в конец списка.
2. **Стена вообще не меняет ничью дистанцию, если закрывает ребро между клетками с
   одинаковым расстоянием.** Между связанными клетками BFS-расстояние отличается ровно
   на единицу или не отличается вовсе; ребро между равными не лежит ни на одном
   кратчайшем маршруте. Обе карты расстояний и так построены для упорядочивания, так что
   это четыре чтения массива вместо заливки — и если ни одно из двух рёбер стены не
   является шагом, то ничего не сдвинулось и никого не могло запереть.

Второе — точное утверждение, на которое поиск опирается: ошибочно разрешённая стена
это нелегальный ход. Поэтому оно проверяется перебором в `Quoridor.Selftest` (115 тысяч
постановок, ноль расхождений). Экономия скромнее, чем хотелось: маршрут не меняется
лишь у 29% постановок. Зато там, где расстояния всё равно нужны, поиск пути заодно
служит проверкой легальности — запертому игроку возвращается −1.

На мелкой глубине, где эффект стены никто не спрашивает, считать маршруты ради
легальности было бы дороже, чем экономия: там работают два дешёвых фильтра подряд —
«маршрут не изменился» и `WallGraph`.

```
                     до оптимизаций      +1 раунд        +2 раунда
дебют, 1 с           9 пх, 722k/с       10 пх, 889k/с   10 пх, 1164k/с
миттельшпиль, 1 с    8 пх, 519k/с        9 пх, 832k/с   10 пх, 1232k/с
миттельшпиль, 0.1 с  6 пх                7 пх            8 пх
```

Итого **+2 полухода глубины** и скорость узлов выросла в 1.7 раза.

### Потоки: отрицательный результат

Lazy SMP реализован (`SearchAgent(threads: N)`), таблица для этого потокобезопасна без
блокировок, вспомогательные потоки расходятся по разным вторым ходам в корне. Замеры:

```
8 потоков : 1 поток   7 : 13    до правки вытеснения
8 потоков : 1 поток   6 : 13    после
```

Потоки не просто бесполезны — они **вредят**, и гипотеза о причине не подтвердилась.
Я предполагал, что помощники вымывают из таблицы глубокие записи главного потока, и
переделал вытеснение под это (см. выше). Картина не изменилась вообще — значит дело в
другом, и следующему, кто возьмётся, стоит начинать не с таблицы.

Движок по умолчанию однопоточный. Код оставлен: он корректен, просто выключен.

### Замеры

```
dotnet run --project tests/Quoridor.Bench -c Release -- depth|fixed|ladder|duel|ablate|smp|trace
```

Ключевое, что стоит гонять после любой правки, — `fixed` и `duel`. Сравнение с более
слабым соперником обманывает: оно смешивает качество оценки с тем, как поиск
масштабируется по глубине. Именно на этом ранняя версия и попалась.

Текущее состояние (по 12–24 партии со случайными дебютами):

```
глубина 4 : глубина 2      21 : 3    (24 партии)
глубина 6 : глубина 4      14 : 9    (24 партии)
глубина 4 : эвристика      23 : 1    (24 партии)
1500 мс   : 50 мс          10 : 6
50 мс     : эвристика      15 : 1
8 потоков : 1 поток         6 : 13   (потоки вредят, см. выше)
история off : история on   11 : 13   (в пределах шума)
```

На 12 партиях та же лестница глубин однажды дала 6:5 вместо 14:9 — полезное
напоминание, что на этой выборке шум съедает почти любой вывод.

## Просмотр истории

Любую партию можно отлистать назад — стрелками, кнопками или кликом по строке журнала.
Пока вы смотрите, **часы стоят и движки молчат**: партия, которая продолжается за вашей
спиной, каждый раз возвращала бы вас туда, откуда вы ушли. Кнопка **Live** догоняет.

## Настройки

Кнопка **Settings** в подвале меню. Тема, время на ход движка (0.4 / 1.2 / 3 с), темп
наблюдаемой партии (brisk / steady / calm) и показывать ли маршруты всегда. Хранится в
`%APPDATA%\Quoridor\settings.json`; битый или отсутствующий файл просто означает
значения по умолчанию — настройка не стоит того, чтобы из-за неё падать.

## Меню

Рядом с меню идёт настоящая партия: тот же `BoardView` и тот же движок, что и в игре,
просто без взаимодействия. Оба игрока — `SearchAgent` на коротких часах (90 мс),
дебютные два-пять ходов случайные, иначе два одинаковых движка играли бы одну и ту же
партию бесконечно. Случайный дебют заодно быстро выводит стены на доску.

Одноходовая эвристика для этого не годится: при честной цене стены она почти никогда
её не тратит, и получаются две точки, которые расходятся мимо друг друга.

## Интерфейс

Визуальная идея — **чернила по бумаге**, а не тёмный дашборд. Светлая тема: тёплый
костяной лист и типографская краска. Тёмная — та же краска, только лист убрали,
поэтому серые остаются тёплыми и не сваливаются в сине-чёрный, куда по умолчанию
уезжает любой тёмный интерфейс. Игроки — бирюза и жжёная киноварь: различимы мгновенно
и обе достаточно приглушены, чтобы не кричать с бумаги.

Три шрифтовых голоса, и они не пересекаются. Sitka (текстовая антиква) несёт имена
вещей: логотип, меню, результат. Sitka курсивом в малом кегле подписывает разделы —
так в вёрстке отбивают подпись. Segoe UI — всё, что нужно быстро прочесть. Consolas —
всё, что на самом деле число: журнал ходов и координаты доски.

Группировка — тонкой линейкой, а не рамкой. Заключать каждую группу в коробку — ровно
то, от чего интерфейс выглядит собранным из готовых блоков. Радиусы скруглений мелкие
(3–5 px): резкая геометрия читается как намеренная.

У доски есть поля с координатами `a`–`i` и `1`–`9`, как у настоящей, и финишная линия
вдоль дальнего ряда в цвете игрока. Недопустимая стена показывается пустым контуром, а
не красной заливкой — не нужен предупреждающий цвет, который спорил бы с цветом игрока.

Ещё три вещи, которые доска показывает, а физическая — нет:

* **Стены в цвете владельца.** В настольной версии фишки стен нейтральные, но на экране
  это разница между «прочитать позицию с одного взгляда» и «восстанавливать, кто что
  построил». Владелец хранится в `GameState.WallsByPlayer1` и намеренно не входит в
  Zobrist-хеш: на игру он не влияет, а без него две одинаковые по сути позиции делят
  одну запись в таблице транспозиций.
* **Метка последнего хода.** Бот отвечает, пока вы смотрите в сторону; без метки
  приходится сравнивать доску с тем, что помнишь.
* **Маршруты** по `Space` — пунктир кратчайших путей обоих игроков. Quoridor это игра
  про длину маршрута, а маршрут — единственное, чего доска не показывает.
* **Цена стены под курсором** — «costs them 2 steps, and nothing to you». Проверка
  легальности и так проходит оба маршрута, так что число, ради которого стену и ставят,
  достаётся практически даром.

В партии против сильного бота под статусом идёт строка вида `depth 11 · 1.4M nodes ·
bot ahead`: видно, насколько глубоко он посчитал и как оценивает позицию.

Тема — общие экземпляры `SolidColorBrush` в `Application.Resources`, на которые всё
ссылается через `DynamicResource`. Переключение темы не перестраивает визуальное
дерево: анимируется `Color` этих кистей, и окно перекрашивается целиком за один
проход.

Одна тонкость: WPF замораживает любой `Freezable`, попавший в `Application.Resources`,
а замороженную кисть анимировать уже нельзя. Поэтому `Palette.Install` вешает на
каждую кисть удерживаемую анимацию нулевой длины — с активным клоком `CanFreeze`
возвращает `false`, и кисть остаётся редактируемой.

Доска (`BoardView`) рисуется в фиксированных логических координатах 728×728 внутри
`Viewbox`, поэтому геометрия не зависит от размера окна и от DPI.
